# Журналы WAL и контрольные точки PostgreSQL

## Цель работы

1. Настроить выполнение контрольной точки (checkpoint) раз в 30 секунд.
2. В течение 10 минут нагрузить кластер утилитой `pgbench`, оценить объём сгенерированных журнальных (WAL) записей и средний объём на одну контрольную точку.
3. По статистике проверить, выполнялись ли контрольные точки строго по расписанию, и объяснить отклонения.
4. Сравнить TPS при синхронном и асинхронном подтверждении коммита (`synchronous_commit`).
5. Создать кластер с контрольными суммами страниц, повредить данные таблицы на диске и описать поведение СУБД и способы «игнорирования» ошибки.

## Часть 1. Настройка контрольных точек раз в 30 секунд

### Параметр `checkpoint_timeout`

Исходное значение: **5 min**.

```sql
ALTER SYSTEM SET checkpoint_timeout = '30s';
```

После `ALTER SYSTEM` требуется **перезапуск кластера** — до рестарта в сессии по-прежнему отображалось `5min`; после `pg_ctlcluster stop/start 15 ex7` параметр применился:

```text
checkpoint_timeout = 30s
```

## Часть 2. Нагрузка pgbench (10 минут)

### Подготовка схемы

```bash
pgbench -i postgres -p 5434 -U postgres
```

### Прогон нагрузки

```bash
pgbench -p 5434 -c 8 -P 6 -T 600 -U postgres postgres
```

| Флаг | Значение | Назначение |
|------|----------|------------|
| `-c 8` | 8 клиентов | Параллельные сессии |
| `-P 6` | отчёт каждые 6 с | Промежуточный TPS и задержки |
| `-T 600` | 600 с | **10 минут** нагрузки |
| `-p 5434` | порт кластера ex7 | |
| `-U postgres` | пользователь | |

Сценарий: встроенный TPC-B, `scaling factor: 1`, `query mode: simple`.

## Часть 3. Объём WAL и средний объём на одну контрольную точку

### Статистика контрольных точек

После нагрузки (накопительно с момента запуска кластера):

```sql
SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;
```

| checkpoints_timed | checkpoints_req |
|-------------------|-----------------|
| 42 | 1 |

- **42** — контрольные точки по таймеру (`checkpoint_timeout`).
- **1** — одна **внеплановая** checkpoint (чаще всего из‑за заполнения WAL до `max_wal_size` или сильной записи).
### Оценка объёма WAL

Позиция WAL на момент замера:

```sql
SELECT pg_current_wal_lsn();  -- 0/70E6EB8
```

Грубая оценка «среднего на checkpoint» по накопленному смещению LSN и числу checkpoint (42 + 1):

```sql
SELECT x'70e6eb8'::bigint / 43 AS size_per_checkpoint;
-- ≈ 2 753 171 байт (~2,6 MiB на checkpoint)
```

**Вывод:** за период активной работы кластера с частыми checkpoint и нагрузкой pgbench генерируется заметный объём WAL; **усреднённо на одну контрольную точку** (по использованной формуле) получается порядка **~2,6 MiB**.

## Часть 4. Выполнялись ли checkpoint строго по расписанию?

### Наблюдения по TPS (режим `synchronous_commit = on`, по умолчанию)

Итог первого 10‑минутного прогона:

| Метрика | Значение |
|---------|----------|
| **TPS** | **18,58** |
| Транзакций | 11 169 |
| Средняя задержка | 430 ms |
| σ задержки | 681 ms |

На графике по 6‑секундным интервалам видны **регулярные провалы** TPS (до **3–10 tps**) и рост latency (**1–2,3 с**) примерно **каждые 30 секунд** (например, около 60, 90, 150, 210, 270, 330, 390, 450, 510, 570 с от начала теста). Это согласуется с работой **checkpoint**: сброс dirty‑буферов и fsync данных/WAL создаёт пики дисковой нагрузки.

### Почему не «ровно каждые 30 секунд»

1. **Плановая checkpoint не всегда мгновенна** — запись растягивается (`checkpoint_completion_target`), следующая по таймеру может **сдвинуться**, если предыдущая ещё не завершена.
2. **Внеплановая checkpoint** — в статистике **`checkpoints_req = 1`**: сработал дополнительный триггер (типично WAL / `max_wal_size`).
3. **Конкуренция с нагрузкой** — при `synchronous_commit = on` каждая транзакция ждёт сброса WAL на диск; во время checkpoint ожидания **усиливаются**, TPS падает не в идеально фиксированные моменты.

**Ответ:** контрольные точки **ориентировались** на `checkpoint_timeout = 30s`, но **не с точностью секундного таймера**; наличие **1** запрошенной checkpoint и пики I/O в pgbench это подтверждают.

Для проверки по логу (при `log_checkpoints = on`):

```bash
grep -i checkpoint /var/lib/postgresql/15/ex7/pg_log/postgresql-*.log
```

## Часть 5. Сравнение TPS: синхронный и асинхронный commit

### Настройка асинхронного режима

```sql
ALTER SYSTEM SET synchronous_commit = off;
```

После перезапуска кластера ex7 — второй прогон той же командой `pgbench` (10 минут).

### Результаты

| Режим | `synchronous_commit` | **TPS** | Транзакций за 600 с | Средняя latency |
|-------|--------------------|---------|---------------------|-----------------|
| Синхронный | `on` (по умолчанию) | **18,58** | 11 169 | 430 ms |
| Асинхронный | `off` | **8005,45** | 4 805 369 | ~1,0 ms |

Ускорение по TPS: примерно **в 430 раз** (8005 / 18,6).

### Объяснение

При **`synchronous_commit = on`** (уровень `on` / `remote_apply` / `remote_write` в зависимости от настроек) клиент **не получает подтверждение COMMIT**, пока соответствующие записи WAL **не будут надёжно сброшены** на диск. Каждая транзакция pgbench ждёт fsync WAL → при 8 клиентах и частых checkpoint диск становится узким местом, latency растёт до сотен миллисекунд и секунд.

При **`synchronous_commit = off`** подтверждение выдаётся после записи WAL в **разделяемую память** процесса; сброс на диск выполняется **фоном** (walwriter). Транзакции идут почти без ожидания диска → TPS тысячи, latency около 1 ms.

**Компромисс:** при `off` возможна **потеря последних подтверждённых транзакций** при сбое ОС/питания (не при обычном `pg_ctl stop`).

## Часть 6. Контрольные суммы страниц (data checksums)

### Кластер с checksum

```bash
pg_createcluster 15 ex7_cs -- --data-checksums
pg_ctlcluster start 15 ex7_cs
```

В выводе `initdb`: **«Контроль целостности страниц данных включён»**. Порт **5435**.

### Эксперимент

```sql
CREATE TABLE a (b text);
INSERT INTO a SELECT md5(random()::text) FROM generate_series(1, 1000);
SELECT pg_relation_filepath('a');  -- base/5/16388
```

Далее:

1. Остановить кластер: `pg_ctlcluster stop 15 ex7_cs`.
2. Изменить **несколько байт** в файле таблицы на диске (в логе — повреждение **блока 2** файла `base/5/16388`).
3. Запустить кластер и выполнить: `SELECT * FROM a;`

### Результат

```text
ПРЕДУПРЕЖДЕНИЕ:  ошибка проверки страницы: получена контрольная сумма 56356, а ожидалась - 26484
ОШИБКА:  неверная страница в блоке 2 отношения base/5/16388
```

### Что и почему произошло

- При `initdb --data-checksums` для каждой страницы данных хранится **контрольная сумма**.
- При чтении страницы в буфер PostgreSQL **пересчитывает checksum** и сравнивает с сохранённой.
- Ручное изменение файла **в обход СУБД** нарушает содержимое и checksum → СУБД  **прерывает запрос** с ошибкой.

Ошибка возникает **на чтении** повреждённого блока, а не при старте сервера.

### Как «игнорировать» ошибку и продолжить работу

| Способ | Параметр / действие | Поведение |
|--------|---------------------|-----------|
| Игнорировать несовпадение checksum | `ignore_checksum_failure = on` | Неверная checksum — **предупреждение**, чтение **продолжается** (данные могут быть мусором). |
| Обнулить повреждённую страницу | `zero_damaged_pages = on` | При обнаружении повреждения страница **заполняется нулями**, в лог — WARNING, запрос может выполниться с **потерей строк** в этой странице. |

Пример (требуется перезапуск):

```sql
ALTER SYSTEM SET ignore_checksum_failure = on;
-- или
ALTER SYSTEM SET zero_damaged_pages = on;
```

После `pg_ctlcluster restart` повторить `SELECT * FROM a` — поведение изменится согласно выбранному параметру.


---

## Краткие выводы

1. **`checkpoint_timeout = '30s'`** задаёт **целевой** интервал плановых checkpoint; фактическое время «плавает» из‑за длительности сброса, `checkpoint_completion_target` и внеплановых checkpoint (`checkpoints_req`).
2. Частые checkpoint при синхронном commit и нагрузке pgbench **сильно снижают TPS** (~19 tps); при `synchronous_commit = off` — **~8000 tps** при той же нагрузке.
3. Объём WAL за период нужно считать по **дельте LSN**; деление полного LSN на число checkpoint из `pg_stat_bgwriter` даёт **грубую** оценку (~2,6 MiB/checkpoint в выполненном расчёте).
4. Кластер с **data checksums** **обнаруживает** порчу страниц при чтении; для обхода используют `ignore_checksum_failure` или `zero_damaged_pages`.
