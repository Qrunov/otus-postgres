# Отчёт по домашнему заданию: нагрузочное тестирование и тюнинг PostgreSQL

## Цель работы

1. Развернуть виртуальную машину и установить PostgreSQL 18.
2. Настроить кластер на максимальную производительность (допускается снижение надёжности при аварийной перезагрузке ВМ).
3. Нагрузить кластер утилитой `pgbench` и зафиксировать достигнутый TPS.
4. Описать изменённые параметры, их значения и обоснование.

## Методика нагрузочного тестирования

Использовалась встроенная утилита [pgbench](https://postgrespro.ru/docs/postgrespro/18/pgbench) в режиме TPC-B (встроенный сценарий).

**Команда (одинаковая до и после тюнинга):**

```bash
pgbench -c 50 -j 2 -P 10 -T 300 test -p 5433 -U postgres
```

| Флаг | Значение | Назначение |
|------|----------|------------|
| `-c 50` | 50 клиентов | Одновременные сессии, имитирующие нагрузку |
| `-j 2` | 2 потока | Параллельная отправка запросов от клиентов |
| `-P 10` | отчёт каждые 10 с | Промежуточный TPS и задержки |
| `-T 300` | 300 с | Длительность теста (5 минут) |
| `test` | БД | База с предварительно инициализированной схемой pgbench |
| `-p 5433` | порт | Подключение к настроенному кластеру |

Перед каждым прогоном выполнялся `VACUUM` (строка `starting vacuum...end.` в выводе).

## Настройка параметров PostgreSQL

Все изменения — через `ALTER SYSTEM SET ...` (сохраняются в `postgresql.auto.conf`), затем `SELECT pg_reload_conf();` или перезапуск, где параметр этого требует.

### Память и планировщик

| Параметр | Было | Стало | Зачем |
|----------|------|-------|--------|
| `shared_buffers` | 128 MB | **16 GB** | Основной кэш страниц в shared memory. Для OLTP и pgbench увеличение снижает чтение с диска; при достаточной RAM на ВМ (ориентир — 25–40% RAM) это главный рычаг пропускной способности. |
| `effective_cache_size` | 4 GB | **24 GB** | Подсказка планировщику «сколько данных уже в кэше ОС + PostgreSQL». Завышение относительно реальной RAM на ВМ не ускоряет сам по себе, но побуждает выбирать index scan вместо seq scan; значение подобрано под объём RAM ВМ. |
| `work_mem` | 64 MB | **160 MB** | Память на сортировку/хеш в одной операции запроса. Для pgbench (короткие UPDATE/SELECT)  |

### Параллелизм и фоновые процессы

| Параметр | Было | Стало | Зачем |
|----------|------|-------|--------|
| `max_worker_processes` | 8 | **16** | Верхняя граница фоновых воркеров (в т.ч. для parallel query и служебных процессов). Запас под параллельные планы и расширения; для чистого pgbench эффект вторичен, но согласован с увеличением нагрузки. |
| `autovacuum` | on | **off** | Autovacuum во время бенчмарка конкурирует за I/O и CPU. Отключение убирает фоновые VACUUM/ANALYZE и стабилизирует TPS на коротком тесте; **для продакшена недопустимо** надолго. |

### WAL, checkpoint и «небезопасная» запись

| Параметр | Было | Стало | Зачем |
|----------|------|-------|--------|
| `fsync` | on | **off** | Не принуждает ОС сбрасывать данные на диск при commit. Резко снижает latency записи; при сбое питания/ядра данные в БД могут оказаться повреждёнными. Соответствует условию ДЗ про игнор надёжности при аварийной перезагрузке. |
| `full_page_writes` | on | **off** | Не пишет полные копии страниц в WAL после checkpoint. Меньше объём WAL и I/O; при краше во время записи страница может не восстановиться. |
| `synchronous_commit` | on | **off** | Commit не ждёт сброса WAL на диск. Клиент получает успех раньше; при падении возможна потеря последних транзакций. |
| `wal_level` | replica | **minimal** | Минимальный объём информации в WAL (без логической репликации/архивирования на уровне replica). Меньше накладных расходов на запись WAL. |
| `checkpoint_timeout` | 5 min | **60 min** | Реже принудительные checkpoint → меньше всплесков записи и пауз в TPS на длинном прогоне. |

### I/O (для SSD/NVMe)

| Параметр | Было | Стало | Зачем |
|----------|------|-------|--------|
| `effective_io_concurrency` | 1 | **200** | Сколько одновременных операций чтения PostgreSQL «ожидает» от диска. Для SSD высокое значение позволяет prefetch и bitmap heap scan лучше загружать очередь I/O; для HDD обычно ставят 2–4. |

## Почему такой скачок TPS

До тюнинга узкие места типичны для «консервативного» кластера на OLTP-нагрузке:

1. **Маленький `shared_buffers` (128 MB)** — большая часть рабочего набора уходит на диск.
2. **Строгая durability** (`fsync`, `synchronous_commit`, `full_page_writes`, `wal_level = replica`) — каждая транзакция pgbench платит за синхронную запись WAL.
3. **Частые checkpoint** и **autovacuum** — дополнительные паузы и I/O.

После тюнинга рабочий набор pgbench (scale factor 1 — небольшая БД) **помещается в 16 GB shared_buffers**, запись идёт **без ожидания диска**, фоновая уборка отключена на время теста — отсюда порядка **34-кратного** роста TPS и падение средней задержки с ~220 ms до ~6 ms.

---

## Риски (осознанно принятые по условию ДЗ)

При `fsync = off`, `full_page_writes = off`, `synchronous_commit = off`, `wal_level = minimal`:

- после аварийного выключения ВМ возможны **повреждение данных** и **потеря последних транзакций**;
- восстановление до согласованного состояния **не гарантируется**;
- репликация  в такой конфигурации **нецелесообразна**.

## Приложение: команды применения настроек

```sql
ALTER SYSTEM SET max_worker_processes = 16;
ALTER SYSTEM SET work_mem = '160MB';
ALTER SYSTEM SET autovacuum = off;
ALTER SYSTEM SET effective_io_concurrency = 200;
ALTER SYSTEM SET checkpoint_timeout = '60min';
ALTER SYSTEM SET fsync = off;
ALTER SYSTEM SET full_page_writes = off;
ALTER SYSTEM SET wal_level = minimal;
ALTER SYSTEM SET synchronous_commit = off;
ALTER SYSTEM SET effective_cache_size = '24GB';
ALTER SYSTEM SET shared_buffers = '16GB';
```

После изменений — перезагрузка конфигурации или рестарт кластера, затем повторный прогон `pgbench` той же командой, что в разделе «Методика».
